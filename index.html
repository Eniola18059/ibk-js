1. What a computer actually does with your code

Let's start further back than most tutorials do. A computer, at its core, is an extremely fast, extremely obedient, but extremely literal-minded machine. It cannot "understand" ideas the way you do. All it can really do is move numbers around in memory and follow yes/no comparisons. Everything you'll ever write in JavaScript — no matter how advanced it looks later — eventually gets broken down into that kind of simple, mechanical instruction.

So when you type JavaScript code into a file and run it, something has to translate your human-readable words (let, if, function) into those low-level instructions. That translator is called a JavaScript engine. Every browser has one built in — Chrome and Node.js both use an engine called V8, Firefox uses one called SpiderMonkey, and Safari uses JavaScriptCore. You don't need to know how these work internally. You just need to know that something is reading your code, top to bottom, one instruction at a time, and carrying it out.

In Plain English

Think of it like a recipe: you (the programmer) write a recipe in a language a chef (the engine) can read. The chef doesn't improvise or guess your intentions — it follows the recipe exactly as written, one step at a time, in order. If you write the steps in the wrong order, or leave one out, the dish comes out wrong. This is why precision matters so much in programming, and why we spend so much time being exact about spelling, punctuation, and order.

Now, what does the engine actually store while it works? Memory. Imagine your computer's memory as an enormous wall of small storage lockers, each one able to hold a single value. When your program needs to remember something — a name, a number, a list — the engine finds a free locker, puts the value inside, and gives that locker a label so your code can find it again later. That labeled locker is what we call a variable, and it's the very first real concept we'll dig into.

Quick self-check before moving on: Can you explain, in your own words, what a "JavaScript engine" does? If you can say "it reads my code and carries out the instructions in order," you're ready for Section 2.

2. Variables — boxes with names

A variable is simply a name you give to a value so that you (and your code) can refer to it later without retyping it. Instead of writing the number 25 everywhere in your program, you write it once, give it a name like age, and then use age everywhere you need that value.

let name = "Eniola";
console.log(name); // prints: Eniola

Let's slow down and read that line by line, because every single word matters:

  • let — a keyword telling JavaScript "I am about to create a new variable."
  • name — the label we're choosing for this variable. We could have called it anything (myName, x, userFirstName) — the word name has no special meaning to JavaScript, it's just a label we chose because it's descriptive.
  • = — the assignment operator. This does NOT mean "equals" the way it does in math. It means "take the thing on the right, and store it in the box on the left."
  • "Eniola" — the actual value being stored. The quotation marks tell JavaScript "this is text, not code to run."
  • ; — a semicolon, marking the end of the instruction. Think of it as a full stop at the end of a sentence.

The second line, console.log(name), is a way of asking JavaScript to print a value so a human can see it. console refers to your browser's or Node's built-in debugging console; .log(...) is an instruction meaning "write whatever's inside these parentheses out for me to read." You will use console.log constantly — it's your window into what your program is actually doing.

The three ways to create a variable

JavaScript actually gives you three different keywords for creating a variable box: var, let, and const. Beginners often ask "why three?" — the honest answer is historical: var is the original, from JavaScript's creation in 1995. As the language matured, developers realized var had confusing rules (you'll see exactly why in Section 3), so in 2015 JavaScript introduced let and const as safer replacements. Today, well-written JavaScript almost never uses var.

const — the "locked" box

const is short for "constant," meaning a value that does not change. Once you store a value with const, you cannot put a different value in that same box later.

const pi = 3.14159;
pi = 4; // ❌ TypeError: Assignment to constant variable.

Notice the engine doesn't just ignore your mistake — it stops your entire program and shows you an error. This is actually a helpful safety feature: if you know a value should never change (like pi, or a person's date of birth once recorded), locking it with const means JavaScript will catch you if you — or a future version of you, six months from now, who's forgotten this code — accidentally try to overwrite it.

Important subtlety, explained slowly: const only locks the box itself, not necessarily what's inside it — if what's inside is an object or array. You cannot replace the box's entire contents, but if the contents are a container (like an object), you can still reach inside that container and change its individual pieces. This will feel confusing right now and is explained fully with examples in Section 4 — for now, just remember: const means "you can't reassign this variable," not "this value can never change in any way."

let — the "refillable" box

Use let when you know the value stored will need to change later — for example, a score that goes up, or a countdown that goes down.

let score = 0;
score = score + 1; // take the current value of score, add 1, store the result back into score
console.log(score); // 1

Read that middle line very carefully, because it confuses almost every beginner the first time: score = score + 1 is NOT a mathematical claim that "score equals score plus one" (which would be nonsense in math). Remember, = means "store the result of the right side into the box on the left." So JavaScript first calculates the right-hand side (looks up score's current value, which is 0, and adds 1, getting 1), and only afterward does it store that new result, 1, back into the score box — overwriting the old value of 0.

var — the old way (avoid it, but recognize it)

You'll still encounter var in older code, tutorials, and StackOverflow answers from before 2015. It behaves similarly to let — you can reassign it — but its scoping rules (Section 3) are looser and cause real bugs. The modern convention, which you should follow from day one, is: never write var in new code.

The simple decision rule: Start every variable as const. If you later find you genuinely need to reassign it, change it to let. Never reach for var.

Naming your variables

JavaScript has strict technical rules and separate stylistic conventions for naming.

Technical rules (the language enforces these): A name can contain letters, digits, underscores (_), and dollar signs ($). It cannot start with a digit. It cannot be one of JavaScript's reserved words (like let, if, or function themselves). Names are case-sensitive, meaning age and Age are two completely different, unrelated boxes.

Stylistic convention (the community agrees on this, but JS won't stop you from breaking it): use camelCase — the first word lowercase, every following word capitalized, no spaces or underscores: firstName, totalScore, isLoggedIn. This isn't a JavaScript rule, it's a readability habit shared by virtually all JS developers, so following it makes your code look "normal" to others (and to future you).

Also, pick names that describe what the value is, not vague single letters. let d = 5; tells a reader nothing. let daysRemaining = 5; tells them everything.

Try it yourself Open your browser: right-click anywhere on a webpage → "Inspect" → click the "Console" tab. This is a live JavaScript environment. Type each of these lines, pressing Enter after each one, and watch what happens: 
const myName = "your actual name here";
console.log(myName);
let myAge = 20;
myAge = myAge + 1;
console.log(myAge);
Then try typing myName = "someone else" and press Enter — you should see an error. Read the error message carefully; it's telling you exactly what we discussed above.

3. Scope — who can see which box

Scope is one of the ideas beginners find most confusing at first, but the underlying concept is simple once you have the right picture in your head. Scope answers the question: "from this exact line of code, which variables am I allowed to see and use?"

In Plain English

Picture a set of rooms inside rooms — like a house with a living room, and inside the living room, a smaller closet. Anything left in the living room (the outer room) can be seen and used by someone standing in the closet (the inner room). But something left inside the closet cannot be seen or used by someone standing out in the living room, because the closet is a private space nested inside the bigger one. JavaScript's "rooms" are created by curly braces { } and by functions.

Global scope — the outermost room

A variable declared outside of any function or block of curly braces lives in the global scope. This is the "outdoors" — visible from literally anywhere else in your file.

const appName = "Noveltiq"; // declared globally — outside everything

function greet() {
  console.log(appName); // ✅ visible here, because greet() is "inside" the global room
}

greet(); // prints: Noveltiq

Function scope — a private room created by a function

Every time you write a function, you are creating a brand-new private room. Any variable declared inside that function — using let, const, or var — only exists while that function is running, and is completely invisible to code outside it.

function calculateTotal() {
  const tax = 0.075; // this variable only exists inside calculateTotal
  const total = 100 * (1 + tax);
  return total;
}

console.log(calculateTotal()); // 107.5 — fine, we called the function
console.log(tax); // ❌ ReferenceError: tax is not defined

Why does this error happen? Because tax was created inside the "room" belonging to calculateTotal. Once that function finishes running, its room — and everything declared inside it — is gone. Trying to access tax from outside is like trying to grab something from a room that's already been demolished.

Block scope — a private room created by any { }

A "block" is any section of code wrapped in curly braces: the body of an if statement, a loop, or even a standalone pair of braces with nothing else around them. let and const both respect block scope, meaning a variable declared inside { } does not exist outside those braces.

if (true) {
  let secret = "hidden";
  console.log(secret); // ✅ works — we're still inside the block
}

console.log(secret); // ❌ ReferenceError: secret is not defined

This is exactly the same "room" logic as function scope, just applied to any curly braces, not only function ones.

The var trap — why the old keyword causes bugs

This is important: var completely ignores block scope. It only respects function scope. That means a var declared inside an if block "leaks" out of that block and becomes visible outside it — as long as it's still within the same function (or the global scope, if there's no enclosing function).
if (true) {
  var leaky = "I escaped the block!";
}
console.log(leaky); // "I escaped the block!" — var does NOT respect the { }

Why is this a problem in practice? Imagine a large program with many if blocks and loops, all using var. A variable you thought was safely "contained" inside one block might actually be visible — and accidentally overwritten — somewhere else entirely in the same function, causing bugs that are very hard to trace back to their source. This single issue is the main historical reason the language introduced let and const in the first place.

Try it yourself Write a function with an if block inside it. Inside the if block, declare a variable using let and give it any value. Immediately after the closing brace of the if block — but still inside the function — try to console.log that variable. You should get an error. Then repeat the exact same experiment but declare the variable with var instead, and notice the difference. Write one sentence explaining, in your own words, why the results differ.

4. Data types — the kinds of things you can store

Every single value in JavaScript belongs to one of two big families: primitives and reference types. Understanding the difference between these two families now will save you from a huge number of confusing bugs later, so we're going to go slowly and use several examples.

Primitive types — simple, single values

A primitive is a basic, indivisible value — it can't be broken down into smaller pieces, and it can't have things added to it after creation. JavaScript has 7 primitive types. You'll use 5 of them constantly; the other 2 are rare and safe to ignore for now.

let a = "hello world";  // string — text, always wrapped in quotes (' " or `)
let b = 42;               // number — JS has only ONE number type; no separate "integer" vs "decimal"
let c = true;              // boolean — exactly two possible values: true or false
let d = undefined;         // a variable that exists but has not been given a value yet
let e = null;               // a value YOU deliberately set to mean "intentionally nothing"
// (BigInt and Symbol exist too, but you won't need them for a long time — skip them for now)

Let's clarify a subtlety that confuses many beginners: undefined vs null. Both seem to mean "nothing," but the difference is about who caused it. undefined is JavaScript's own automatic default — if you declare a variable and never give it a value, JavaScript fills it with undefined for you. null, on the other hand, is something a programmer writes deliberately, to say "I am intentionally recording that there is no value here" — for example, a "middle name" field for someone who doesn't have one.

let middleName; // declared, but no value given
console.log(middleName); // undefined — JS filled this in automatically

let nickname = null; // WE chose to say "no nickname exists"
console.log(nickname); // null — we set this on purpose

The critical property of primitives: copies are independent

When you copy a primitive value into a new variable, JavaScript creates a totally separate, independent copy. Changing one has zero effect on the other.

let x = 5;
let y = x; // y receives its own independent copy of the value 5
y = 10; // we change y only
console.log(x); // 5 — completely unaffected
console.log(y); // 10

This matches how most people already think about numbers intuitively — if you write "5" on two separate pieces of paper, scribbling on one doesn't change the other. Reference types, which we cover next, behave very differently, and that difference is the whole point of this section.

Reference types — containers that hold other things

Objects and arrays are called "reference types" because of HOW they're stored in memory, which is fundamentally different from primitives. Instead of the variable directly holding the value, the variable holds a "reference" — think of it as an address or a sticky note pointing to where the actual data lives elsewhere in memory.

const person = { name: "Eniola", role: "Founder" }; // an object: a container of labeled properties
const numbers = [1, 2, 3]; // an array: an ordered container of values, accessed by position (0, 1, 2...)

An object groups related pieces of data under descriptive labels (called "properties" or "keys"). You access a property using a dot: person.name gives you "Eniola". An array holds an ordered sequence of items, accessed by a numeric position called an "index," starting at 0 (not 1!): numbers[0] gives you 1, numbers[1] gives you 2.

The critical property of reference types: copies point to the SAME thing

This is the single most important, and most commonly misunderstood, concept in this entire unit. When you copy a reference type into a new variable, you are NOT creating a new, independent object. You're creating a second sticky note pointing at the exact same underlying object. Changing the object through either variable affects what you see through both.

const objA = { count: 1 };
const objB = objA; // objB is NOT a new object — it's a second reference to the SAME object as objA
objB.count = 99; // we reach inside and change a property
console.log(objA.count); // 99 — objA "sees" the change too, because they're the same underlying object!

Read that again slowly if it doesn't click immediately — nearly everyone needs to read this two or three times. objA and objB are two different names, but they both point at one single object sitting in memory. There is only one { count: ... } object in existence here, not two.

Now recall the earlier const subtlety from Section 2 — this is exactly what it was hinting at:

const objA = { count: 1 };
objA = { count: 2 }; // ❌ Error — this tries to make objA point at a DIFFERENT object entirely, which const forbids
objA.count = 2; // ✅ fine — we're not changing what objA points to, just editing the object it already points to

const only prevents you from making the variable point somewhere else. It places no restriction whatsoever on editing the contents of the thing it's already pointing to.

Checking a value's type with typeof

The typeof operator lets you ask JavaScript, "what kind of value is this?" It returns the type as a string.

typeof "hello"    // "string"
typeof 42          // "number"
typeof true         // "boolean"
typeof undefined    // "undefined"
typeof null         // "object"  this is a famous, decades-old bug baked into the language, just memorize it
typeof {}           // "object"
typeof []           // "object"  arrays are technically a specialized kind of object under the hood
Try it yourself In your console, create one variable for each primitive discussed (string, number, boolean, undefined, null) and log the typeof each one. Then create an object called me with at least three properties describing yourself (e.g., name, city, role). Then write const meCopy = me;, change one property through meCopy, and confirm — by logging me — that the original also changed. This exercise is the single most important one in this unit; don't skip it.

5. Operators and coercion — combining values

Arithmetic operators

These work mostly as you'd expect from school math, with one addition (the remainder operator) that's new to most beginners.

5 + 3   // 8    addition
5 - 3   // 2    subtraction
5 * 3   // 15   multiplication
5 / 3   // 1.6666666666666667   division
5 % 3   // 2    remainder ("modulo") — what's left over after dividing 5 by 3 as many whole times as possible (once, with 2 left over)
5 ** 2  // 25   exponent — 5 raised to the power of 2

The remainder operator (%) feels unfamiliar at first but is extremely useful — it's the standard way to check things like "is this number even or odd?" (a number is even if number % 2 equals 0) or "has this counter wrapped back around?" You'll use it constantly.

Comparison operators

5 > 3     // true
5 < 3     // false
5 >= 5    // true (greater than OR equal to)
5 == "5"   // true  — "loose equality": converts types before comparing
5 === "5"  // false — "strict equality": checks BOTH the value AND the type
Always prefer === and !== over == and !=. The loose versions silently convert one side's type to try to make the comparison "work," which produces results that surprise almost everyone at first — for example, 0 == false evaluates to true, and "" == false also evaluates to true. The strict versions never do this silent conversion, so what you see is exactly what's being compared — no hidden surprises.

Logical operators

true && false   // false — AND: the whole expression is only true if BOTH sides are true
true || false   // true  — OR: the whole expression is true if AT LEAST ONE side is true
!true            // false — NOT: flips a boolean to its opposite

A useful way to remember these: && is strict ("everyone has to agree"), || is lenient ("just one yes is enough"), and ! is a mirror that reverses whatever it's given.

Type coercion — JavaScript quietly converting types for you

Coercion is what happens when JavaScript automatically converts a value from one type to another so that an operation can be completed. Sometimes this is convenient; sometimes it produces results that look bizarre until you understand the rule behind them.

"5" + 3      // "53"   the number 3 is converted into the string "3", then joined onto "5"
"5" - 3      // 2       here, the string "5" is converted into the number 5, because subtraction only makes sense between numbers
"5" * "2"    // 10      both strings are converted to numbers
true + 1     // 2       true is converted to the number 1
false + 1    // 1       false is converted to the number 0

Here's the underlying rule, stated plainly: the + operator prefers to combine values as text (this is called "concatenation") whenever at least one side is already a string. Every other arithmetic operator (- * / %) has no text-combining meaning at all, so JavaScript always forces both sides into numbers first.

Truthy and falsy values

Whenever JavaScript needs a value to behave as a boolean — most commonly inside an if statement's condition — it doesn't require an actual true/false. Instead, it converts whatever value is given into either "truthy" (behaves like true) or "falsy" (behaves like false). There are exactly six falsy values in the entire language. Memorize this short list, because absolutely everything else — no exceptions — is truthy:

false, 0, "", null, undefined, NaN
// literally everything else is truthy — including things that feel "empty," like [] and {}
The trap that catches almost everyone at least once: an empty array [] and an empty object {} are BOTH truthy, even though intuitively they feel like they should mean "nothing." Only the six exact values listed above are falsy — everything else, no matter how "empty" it looks, is truthy.
if ([]) {
  console.log("this actually runs!"); // yes, it does — [] is truthy
}
Try it yourself Predict the result of each of these lines before typing them into your console, write down your guess, then check: "3" + 3, "3" - 3, 3 === "3", Boolean(""), Boolean("0"), Boolean([]). The last three are the ones that trip people up the most — make sure you can explain out loud why each one is true or false.

6. Control flow — decisions and repetition

if / else if / else — making decisions

An if statement runs a block of code only when its condition is truthy. You can chain multiple checks together with else if, and provide a fallback with a final else.

const age = 20;

if (age >= 18) {
  console.log("You can vote.");
} else if (age >= 13) {
  console.log("You're a teenager.");
} else {
  console.log("You're a child.");
}
// prints: You can vote.

JavaScript checks these conditions in order, from top to bottom. The moment it finds one that's truthy, it runs that block and skips every remaining else if/else below it — it never checks further once it's found a match. In our example, age >= 18 is truthy (20 is indeed at least 18), so JavaScript runs that first block and never even evaluates the other two conditions.

switch — comparing one value against several exact options

When you're comparing one single variable against many possible exact values, a switch statement is often easier to read than a long chain of else ifs.

const day = "Monday";

switch (day) {
  case "Saturday":
  case "Sunday":
    console.log("Weekend!");
    break;
  case "Monday":
    console.log("Start of the work week.");
    break;
  default:
    console.log("Midweek.");
}
// prints: Start of the work week.

Each case is compared to day using strict equality. When a case's value matches, its code runs. Notice "Saturday" and "Sunday" share the same block by being stacked with no code in between — this is intentional and means "if it's either of these, do the same thing." The default case is a fallback, similar to a final else, running only if none of the cases matched.

Never forget the break keyword. Without it, JavaScript doesn't stop after a matching case — it keeps running every case below it too, a behavior called "fall-through." This is almost never what you want, and forgetting break is one of the most common switch-statement bugs.

Loops — repeating an action

The for loop is used when you know roughly how many times you want to repeat something, or you want a running counter.

for (let i = 0; i < 5; i++) {
  console.log(i);
}
// prints: 0, 1, 2, 3, 4 (each on its own line)

A for loop has three parts separated by semicolons, and it's worth understanding exactly what each one does and when it runs:

  • let i = 0 — runs ONCE, right at the very start, to set up a counter variable.
  • i < 5 — checked BEFORE every single pass through the loop. If it's truthy, the loop body runs; if it's falsy, the loop stops immediately.
  • i++ — runs AFTER every pass through the loop body finishes, and simply means "increase i by 1" (it's shorthand for i = i + 1).

So the actual order of events is: set i to 0, check i < 5 (true), run body printing 0, increase i to 1, check i < 5 (true), run body printing 1, and so on, until i becomes 5, at which point i < 5 is false and the loop stops.

The while loop is used when you don't know exactly how many repetitions you'll need in advance — you just want to keep going as long as some condition holds.

let attempts = 0;
while (attempts < 3) {
  console.log("Attempt number " + attempts);
  attempts++;
}
// prints: Attempt number 0, Attempt number 1, Attempt number 2
The infinite loop trap: if you forget to change the condition variable inside the loop body (forget the attempts++ above, for instance), the condition never becomes false, and your program will run forever, freezing your browser tab. Always double-check that whatever your loop's condition depends on is actually being updated somewhere inside the loop.

The for...of loop is the simplest, most modern way to walk through every value in an array, one at a time, without needing to manage an index counter yourself.

const fruits = ["apple", "banana", "mango"];
for (const fruit of fruits) {
  console.log(fruit);
}
// prints: apple, banana, mango

Here, fruit is a new variable name we chose (it could be anything), and on each pass through the loop, JavaScript automatically assigns it the next value from the fruits array — first "apple," then "banana," then "mango" — until it's gone through every item.

The for...in loop is used far less often, and walks through the property NAMES (not values) of an object.

const person = { name: "Eniola", role: "Founder" };
for (const key in person) {
  console.log(key, person[key]);
}
// prints: name Eniola
//         role Founder

Here, key takes on each property name in turn ("name," then "role"), and person[key] looks up the corresponding value using that name.

Inside the loop, use an if/else and the remainder operator (%) from Section 5 to print "even" if the number is evenly divisible by 2, and "odd" otherwise. 7. Recap and what's next

Let's summarize everything covered, in plain language, one more time:

  • Your code is read and carried out, line by line, by a JavaScript engine.
  • Variables are named boxes for storing values; use const by default, let when reassignment is needed, and avoid var entirely.
  • Scope determines where a variable is visible; { } and functions create private "rooms," and let/const respect those rooms while var ignores block-level ones.
  • Primitives (string, number, boolean, undefined, null) copy independently; objects and arrays are reference types, where copies point to the same underlying data.
  • Operators combine values, and JavaScript sometimes silently coerces types — memorize the six falsy values so truthy/falsy checks never surprise you.
  • Control flow (if/else, switch, loops) lets your program make decisions and repeat actions.

You now have every concept required for Unit 1's two projects: the CLI calculator (variables, arithmetic and comparison operators, maybe a switch for choosing the operation) and the number-guessing game (variables, comparison operators, a loop, and if/else for feedback). Build both, fully, before moving on to Unit 2 (Functions & Scope) — the projects are where these ideas actually become permanent rather than something you read once and forgot.

Before moving on, make sure you can explain out loud, without looking back at this page: the difference between let and const; why var is avoided; the difference between a primitive and a reference type (and why copying an object is different from copying a number); and why === is preferred over ==. If any of these feel shaky, re-read that section before starting the projects.
